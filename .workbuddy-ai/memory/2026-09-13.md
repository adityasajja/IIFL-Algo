# 2026-09-13 — Paper strategies: fabricated win rates replaced with measurements

## What was wrong

`src/atr/research/papers.py` attached a hardcoded `win_rate` to each of its
7 academic models (0.58, 0.64, 0.60, 0.62, 0.59, 0.65, 0.54) and derived
`expected_value` and `confidence_score` from them, with confidence as literals
(0.85–0.94). The UI presented these as `historical_win_rate`. They were
citations dressed up as measurements — the exact thing the project's
"fact based, not emotional" principle forbids.

## What was done

1. **`scripts/fetch_long_history.py`** (new) — pulls real daily history from
   IIFL into `data/iifl_daily/NSEEQ/`. Fetched **18 large caps × 1,631 bars =
   29,358 symbol-bars, 2020-02-17 → 2026-09-11** (6.5 years). The old cache
   held 249 days, which cannot be carved into folds that also leave warmup.

2. **`scripts/validate_paper_strategies.py`** (new) — walk-forward harness over
   the paper strategies with a **random-selection control** (same universe,
   cadence, sizing; random symbols, 8 seeds).

3. **`src/atr/research/papers.py`** — added a `MEASURED` table with a dated
   snapshot, plus `_stats()` / `_confidence()` helpers. Every hardcoded
   constant is gone.

4. **`src/atr/api/main.py`** — `GET /validation` serves the harness output.

5. **`web/src/ValidationPanel.tsx`** (new) — renders claimed vs measured,
   control baseline, and per-check detail. Wired into ResearchPanel as a
   "Measured results" tab.

## The result — none of the 7 passes

Control (8 runs): **mean Sharpe −0.35** (−1.4% to −38.8% return). Random
selection loses money; that is the floor a signal must clear.

Buy & hold on the same window: **Sharpe +0.69, return +49.31%**. Every claimed

## Bugs found and fixed

- **`Row` does not support `in`.** `paper_alpha.py` guarded with
  `"close" in row`. `Row` subclasses tuple and only overrides `get` /
  `__getitem__`, so `in` hits `tuple.__contains__` and tests *values*, not field
  names — always False. Every paper signal was silently skipped, producing a
  clean-looking "0 trades, no edge" that was really "no data". Fixed to
  `row.get("close")`. **This is the trap: it fails as a plausible result.**
- **Batch evaluator in a per-bar loop.** `run_paper_strategy_evaluator` ran all
  7 models per symbol per bar while each adapter kept one. Added
  `EVALUATORS` / `evaluate_one` and switched the adapter. Walk-forward went from
  >8 min for 5 strategies to ~12 min for 7 + 8 control runs.
- **Sparse snapshot grid silently degrades `history()`.** Feeding one symbol per
  snapshot means `BacktestEngine._build_frames` NaN-pads 99% of each symbol's
  frame, so models see no prices. The feed must put **every symbol on every
  bar**. Documented in `build_feed`.

## Verified

98 tests pass. `bun run build` clean. `/validation` returns 18 symbols, 7
results, control mean −0.35.

## Open

- `min_confidence` on `PaperAlphaBase` now reads the measured deflated Sharpe
  (all < 0.95), so raising it filters almost everything. Intentional, but the
  UI should say so.

Four of the eight have **deep-linkable sub-tabs**: `markets/{scanner,custom,

## Routing — the part that is easy to get wrong

`MarketsTabContainer` used to own its own `useState` for the sub-tab, so
"open this symbol's chart" had nowhere to land: `setTab("charts")` referenced a
tab id that no longer existed and the scanner's chart button silently did
nothing. Sub-tab state was **lifted into `App()`** and the hash became
`#tab/subtab`.

Two compatibility layers, both tested:

- `LEGACY_TABS` maps old ids (`overview`, `scanner`, `charts`, `alerts`,
  `briefing`, `portfolio`, `research`, `backtest`) to their new section.
- `LEGACY_SUB` maps those same ids to the correct *sub-tab*, so `#charts` lands
  on Markets **with Charts open** rather than on the scanner. A redirect that
  lands on the right tab but the wrong panel is still a broken link.

`openChart(symbol)` is the single entry point — it writes `atr.chartSymbol` to
sessionStorage, sets the sub-tab, and navigates. The ticker bar and every
scanner call it.

## Execution mode — paper vs live (new, enforced server-side)

The toggle is one of the six requested features, and it is a **server-side
gate**, not a disabled button:

- `_STATE["execution_mode"]` defaults to `"paper"`.
- `_require_live_execution()` is called by `POST /orders` and
  `POST /trade-signals/{id}/execute`. Read-only endpoints deliberately skip it —
  paper mode must still show the market.
- `POST /risk/execution-mode` rejects `live` without a reason (400).
- `GET /audit` returns an append-only JSONL trail at `data/audit/audit.jsonl`.
  Mode changes, kill-switch actions and orders all land there.

`tests/test_execution_mode.py` — **13 tests**: default-deny, the gate actually
raising, reason required, reason recorded, unknown modes rejected, append-only
(earlier records byte-identical), and survival across a module reload.

## Bug found by those tests

calls would have raised `NameError` the first time they fired. Worse, my new
log call used `{}` placeholders: **`logging` is `%`-style, not
`str.format`**, so `"a {} b {}"` with args raises
`TypeError: not all arguments converted`. Fixed all four call sites to `%s`
and added `logger = logging.getLogger("atr.api")`.

## Two real bugs found while verifying (neither was in the request)

### 1. `/dashboard/summary` read the wrong position field names

It summed `p.get("quantity")` / `last_price` / `avg_price`. But
`IiflClient.positions()` returns **raw camelCase rows** — `netQuantity` /
`averagePrice` / `ltp` (see `IiflBroker.positions`, which uses `_pick` for
exactly this). Result with 3 real positions: **`count: 3` but `value: 0.0,
unrealized_pnl: 0.0`** — a plausible-looking payload that tells the user they
hold nothing. Fixed by moving `_pick` into `main.py` (same contract as the
broker layer) and accepting both spellings, plus skipping `qty == 0` rows the
way `IiflBroker` does.

**Generalise this:** when two layers both map a polymorphic external payload,
they must share one resolver. A second hand-written name list drifts silently.

### 2. The KPI sparkline was the last 7 *trades*, not 7 *days*

`realised[:7]` with `reversed()` drew a line through seven fills in one
afternoon and labelled it a week — and the reversal made it oldest-first while
every other series is newest-first. Replaced with `_trade_day()` bucketing
(Trading day → cumulative running total, oldest → newest), so a quiet session
reads flat instead of collapsing the window. Undated trade → contributes P&L
to the win rate but not to the time series (returns `None`, never "today").

### Also: unknown day P&L was reported as zero

IIFL position rows carry no prior close, and the old code fell back to the
entry price, so `day_pnl` was always ~0. That reads as "unchanged today" for a
book that may be moving hard. Added `day_pnl_complete`; the UI now shows
**`n/a · broker reports no prior close`** instead of a fake `+₹0`.

## CDP gotchas (agent-browser does not support Windows)

- **One reader loop per socket.** Two coroutines calling `ws.recv()` steal each
  other's frames — my first `cmd()` swallowed every `Fetch.requestPaused`, so
  the fixture silently never applied and the capture showed live data while
  looking like it had worked. Route everything through a dispatcher keyed on
  `id`.
- **Wait for the backend before opening the URL.** Point Edge at a dead port
  and it renders its own "refused to connect" error page, which then survives
  `Page.reload` — every assertion reads an empty DOM.
- **Gate on real content, not a fixed sleep**, and not on `h1,h2` (some panels
  have no top-level heading).
- **`innerText` is undefined on detached/void nodes** — always guard.
- The server is reaped at turn end, so launch + probe must share one turn.
- **`pkill -f uvicorn` does not reliably kill the server here.** A stale process
  kept serving *old code* while I verified new code — the payload had no
  `day_pnl_from_cache` key at all, which is what gave it away. Kill by PID from
  `Get-NetTCPConnection -LocalPort 8000` and confirm the port is free before
  restarting. Whenever a verified fix "does not take effect", check for a stale
  listener before touching the code again.

# 2026-09-13 (final) — Day P&L baseline: filled from cache, sanity-bounded

## The follow-up

Populated-state verification showed `day_pnl_complete: false`, meaning Day P&L
would read `n/a` for every real book. Investigated rather than assumed: dumped
the live payload (`scripts/inspect_position_payload.py`) and found
`EC920 No Positions found` — the account is genuinely flat, so IIFL never sent
a prior close *at all*.

Two things separated:

1. **Semantics were wrong.** `day_pnl_complete` was `counted > 0 and all(...)`,
   so an *empty* book reported `False` — implying missing data when the truth
   is "nothing held, 0 change is a complete answer". Now
   `counted == 0 or no_prev == 0`, and the condition is tracked in the loop
   rather than recomputed inline (the inline copy was how it drifted).
2. **A real book still had no baseline.** Added `_prior_closes()`, which reads
   the *named* symbols (not all 2,672) from the local daily cache — 0.41s for
   4 symbols. The broker's own field is still preferred when present.

## Guards, because a stale baseline is worse than a missing one

- **Date guard:** the cache's newest session must be within 4 calendar days of
  today; otherwise return nothing and report Day P&L unknown. A number that is
  silently three weeks old is worse than `n/a`.
- **Sanity bound:** reject a prior close whose gap to the live price exceeds
  35%. Building the fixture exposed this — an invented `ltp` (₹2941.5) against
  the real cached close (₹1257.5) produced **"+52.99% in one day"**, a
  confident fiction. The guard logs the specific mismatch and degrades only
  `day_pnl`; `value` and `unrealized_pnl` stay correct.
- New field `day_pnl_from_cache` records provenance, so "why is Day P&L
  present?" is answerable from the payload.

## Tests — `tests/test_dashboard_summary.py` (13 new, 124 total)

Pins all three outcomes (broker value / cache value / neither), the empty-book
semantics, the absurd-baseline rejection, a plausible +30% session that must be
*kept*, raw camelCase vs snake_case rows, qty-0 rows not counting as positions,
unreadable P&L skipped rather than scored a loss, and that an empty book never
touches the cache. That last one failed first time — `_prior_closes([])` was
still being called; guarded at the call site.

Verified live: `count: 0, day_pnl_complete: True, day_pnl_from_cache: 0`.
Populated capture: `Day P&L + ₹130 · +0.09% on invested` with a rising
sparkline, replacing `n/a`.

# 2026-09-13 (final+) — "Can we rely on this?" → measured answer: NO

## The question

User asked directly: *"can we rely on this to make real trades? can you
backtest and give me results"*. Answered with a fresh multi-split walk-forward,
not reassurance.

## A labelling bug in the validator (fixed)

`validate.py` formatted the significance check as
`"deflated Sharpe >= 0.95: 0.753 vs required Sharpe 0.0456"` — it put a
**probability in [0,1]** and a **Sharpe-ratio number** side by side and called
both "Sharpe". A clear FAIL read as a near-miss against Sharpe 0.046, inviting
the inference that 0.046 would have passed when the bar was 0.95 *probability*.
The *logic* (`dsr >= cfg.min_confidence`) was always right; only the wording lied
about it. Relabelled to `P(edge is real) >= 0.95` with the hurdle named as a
separate quantity, in both the check detail and `summary()`. 3 regression tests;
**proved the guard is real** by temporally reverting the wording → exit 1.

**Generalise:** when a check compares two numbers, the label must name both
quantities. A mislabelled comparison is worse than no comparison, because it is
believable.

## Results — production `SignalEntryStrategy`, 4 fold splits

`scripts/backtest_production_rules.py` (new). 14/18 symbols had long history
(ULTRACEMCO, HCLTECH, TATASTEEL, ADANIENT absent — script now prints this
loudly rather than silently shrinking the universe). 1,631 bars,
2020-02-17 → 2026-09-11.

| train/test | folds | OOS ret | OOS Shrp | B&H Shrp | MaxDD | trades | P(real) | verdict |
|---|---|---|---|---|---|---|---|---|
| 500/250 | 4 | 17.12% | 0.69 | 0.91 | 7.51% | 118 | 0.781 | FAIL |
| 400/200 | 6 | −0.03% | 0.02 | 0.79 | 12.90% | 104 | 0.829 | FAIL |
| 600/300 | 3 | 12.80% | 0.52 | 1.23 | 6.44% | 117 | 0.786 | FAIL |
| 700/350 | 2 | 22.60% | 1.03 | 1.04 | 7.26% | 107 | 0.811 | FAIL |

**0/4 beat buy-and-hold. 0/4 pass. OOS Sharpe spread 0.02–1.03 (spread 1.01)
from the split choice alone** — so any single backtest figure is not
decision-grade.

Separate run via `atr signals validate --train 500 --test 250` (19 symbols incl.
NIFTYBEES, 1,495 bars): 3 folds, 217 trades, OOS 22.13% @ Sharpe 0.60 vs B&H
46.23% @ 1.05 → FAIL on both `P(edge is real)` (0.753 < 0.95) and beats-B&H.

## The decisive result: searching makes the claim WEAKER

`--search` (16 parameter combos → **48 trials**):

| | OOS Sharpe | B&H Sharpe | hurdle | P(edge is real) |
|---|---|---|---|---|
| 3 trials | 0.60 | 1.05 | 0.0456 | **0.753** |
| 48 trials | 0.59 | 1.05 | 0.1012 | **0.343** |

OOS Sharpe barely moved (0.60 → 0.59) while confidence **collapsed 0.753 →
0.343** as the multiple-testing hurdle rose. This is the anti-overfitting
mechanism working exactly as designed, and it is the cleanest demonstration of
the user's "fact based, not emotional" principle in the codebase: trying harder
does not improve the result, it correctly tightens the test.

## Also noted

The production entry rules are referenced by **zero** research scripts or
harnesses apart from `atr signals validate`; the stride stored result was
already `passed: false`. `Scanner.py:77` `score = ret_1m + vs_high` remains an
unvalidated heuristic and `to_date` still defaults to `date.today()`.

127 tests pass.

## Answered: no

Not tradeable — and the honest framing is stronger than "the number is low":
(a) it never clears buy-and-hold, (b) it fails its own significance bar,
(c) the headline number is unstable across splits by more than a full Sharpe
point, and (d) any attempt to tune it lowers, not raises, confidence. The
long-only-inside-an-uptrend shape is structurally disadvantaged on a 2020–2026
large-cap bull window, but that is a secondary point — the statistical
non-significance is benchmark-independent.

# Episodic Pivot (Pradeep Bonde playbook) — measured, and the answer is no

Asked to backtest the playbook on Nifty 50. The playbook (`Pradeep Bonde's
Playbook`, Tradezella Apr 2025) is a discretionary news-driven model: a
**neglected** stock gets a **catalyst** and **re-prices 50–300% in 10–20
sessions**. Worked examples: SMCI +189% in 28 sessions, ROOT +358% in 16,
ANF +240%.

## What was built

- `src/atr/strategy/strategies/episodic_pivot.py` — three variants sharing one
  sizer and one exit engine: `episodic_pivot_day1` (gap-only trigger, the
  faithful day-one entry), `_delayed` (red-to-green after a weak catalyst day,
  the playbook's own Delayed Reaction), `_9m` (volume-only — the playbook's
  "the volume itself is the clue"). A daily bar cannot read an earnings release,
  so the catalyst is proxied by abnormal gap **and** abnormal volume.
- Risk-based sizing (1% of equity to the stop), initial stop below the signal
  bar's low, break-even at 1R, trail under swing lows, optional time stop. The
  stop is a **resting GTC SELL STOP** so it fills at the stop price or the open
  on a gap-through — not at a close.
- `scripts/research_episodic_pivot.py` — the premise study. Measures the pond
  *before* scoring the rules.
- `scripts/validate_episodic_pivot.py` — walk-forward with a **matched control**:
  same symbols, same hold lengths, same weights, **random entry dates**.
- `web/src/EpisodicPivotPanel.tsx` + `GET /validation/episodic-pivot` — both
  studies side by side in Evidence → Measured results.
- Fetched long history for the real constituent lists (official CSVs from
  niftyindices.com → `data/universe/`): Nifty 50 + Midcap 150, 1,567 bars each.

## The premise does not exist on Nifty 50

6.4 years, 49 names, 73,488 symbol-bars:

| | Nifty 50 | Midcap 150 |
|---|---|---|
| gap ≥ 10% | **0** | 33 |
| gap ≥ 20% | **0** | 0 |
| catalyst days (gap≥5% & vol≥3x) | 42 (0.057%) | 191 (0.099%) |
| best 20-session move anywhere | **+71.7%** (TMPV) | +126.7% (SUZLON) |
| 20-session windows > +100% | **0** | 22 |

The playbook calls 20–40% gaps routine. In six years of the Indian benchmark
index there were **none**. And the catalyst itself is not informative: 20-session
forward return after a catalyst was **+2.23% vs +1.77% unconditional** on Nifty
50, and **+0.97% vs +2.24%** on Midcap 150 — i.e. worse than average.

## Out of sample — 0 of 6 pass

Nifty 50: 49 symbols, 1,567 sessions, 400/200/260, 5 bps, 120 trials.
Buy & hold **+96.08%, Sharpe 1.233**. Matched control (same symbols, same hold
lengths, same weights, **random entry dates**).

| variant | OOS return | Sharpe | control | vs control | P(edge) | trades | verdict |
|---|---|---|---|---|---|---|---|
| Day 1 | −0.65% | +0.014 | +0.457 | −0.53σ | 0.155 | 48 | FAIL |
| Delayed | +0.64% | +0.059 | −0.001 | +0.18σ | 0.491 | 61 | FAIL |
| 9M | +18.14% | +0.354 | +0.729 | −1.06σ | **0.961** | 514 | FAIL |

Midcap 150: 129 symbols. Buy & hold **+170.84%, Sharpe 1.457**.

| variant | OOS return | Sharpe | control | vs control | P(edge) | trades | verdict |
|---|---|---|---|---|---|---|---|
| Day 1 | −6.80% | −0.119 | +0.536 | **−1.71σ** | 0.664 | 149 | FAIL |
| Delayed | +7.72% | +0.228 | +0.612 | −0.62σ | 0.286 | 126 | FAIL |
| 9M | +55.85% | +0.744 | +1.038 | −1.23σ | 0.720 | 407 | FAIL |

The 9M variant on Nifty 50 is the interesting one: it is the only rule that
**passes its own significance test** (P=0.961 over 120 trials) and it is still
worthless — Sharpe 0.354 against buy-and-hold's 1.233, and **1.06σ *worse* than
entering the same symbols on random dates**. A real but tiny edge, with timing
that actively hurts. Significance is not usefulness, again.

More damning: **Midcap 150 has the premise Nifty 50 lacks** (33 ten-percent gaps
vs 0, 22 twenty-session windows over +100% vs 0) and the rules still lose there —
Day 1 is 1.71σ worse than random. So this is not merely "wrong pond". The
catalyst-timing premise does not survive measurement on either universe.


## Three framework bugs this uncovered

1. **Uncapped gross exposure.** `SimulatedBroker._can_fund` tests each order
   against total equity *in isolation*, so N concurrent positions are each
   affordable and the book reaches N × equity. This strategy hit **3.49×**.
   Invisible in the trade log; the only symptom was the risk engine reporting a
   "daily loss" of 750k on a 1M account. `RiskLimits.max_gross_exposure` cannot
   fix it — exceeding it *kills* the run via `verdict.allowed == False`. The
   strategy now caps `max_gross_weight`/`max_positions` itself.
2. **`RiskEngine.reset_daily()` never reseeded `day_start_equity`**, so
   `max_daily_loss` was enforced as "cumulative drawdown since inception" — it
   tripped once, permanently, and logged a single-day loss that never happened.
   And the baseline must come from the *rollover*: the engine marks then checks,
   so a baseline seeded inside `check` compares today's equity to itself and the
   limit can never fire on daily bars. Both fixed + regression tests.
3. **`Position.mark()` accepted a NaN price.** `build_feed` writes NaN for a
   symbol with no bar on a step; the NaN became `market_value` → `equity` → the
   whole equity curve → and then `int(nan)` inside an unrelated symbol's sizing.
   It killed 3 of 6 control runs. `Position.mark` now ignores non-finite prices
   and keeps the last known one — which is what `buy_and_hold_equity` already did.

## Vendor data is corrupt on 2021-09-15/16

Scanning both universes found **14 bars at 3–5× the surrounding level, all on
2021-09-15 or 2021-09-16**, across BEL, IRCTC, IPCALAB, JUBLFOOD, KPRMILL, SRF,
SCHAEFFLER. `src/atr/data/hygiene.py` drops them, keyed on **reversion**: the
level 5 sessions before and after must agree with each other while the bar is
far from both. A naive "drop anything far from its neighbours" filter would
delete exactly the episodic moves the research exists to find.

Effect on the premise study: Nifty 50's "best 20-session move" fell from +264%
to **+71.7%**, and 20-session windows over +100% from **20 to 0**. Those numbers
would have been reported as findings.

**188 tests pass** (18 episodic pivot, 10 hygiene, 16 engine).

## Hypotheses and their nulls

| hypothesis | prior | null |
|---|---|---|
| `reversal_short_horizon` | Lehmann 1990, Jegadeesh 1990 | same cadence, same count, **random names** |
| `vol_managed_exposure` | Moreira & Muir 2017 | same exposure sequence, **circularly shifted** |
| `trend_filtered_exposure` | Moskowitz/Ooi/Pedersen 2012 | same, circularly shifted |

The circular shift preserves the exact multiset of exposure values and moves only
the dates — "same sizing, wrong dates". Control gets the **same grid**, so it is
not a weaker null.

## THE method bug that mattered most

The first run reported Nifty 50 reversal at **+2.51σ over its control** — a PASS.
It was measured off **3 control runs**. With 3 seeds (df=2) the one-sided 95%
t-critical is **2.92**, not 2.0. Re-run with 8 seeds: control mean moved 0.466 →
**0.778** and the z collapsed to **+0.56σ**. The PASS was an artefact of a noisy
σ estimate.

`t_critical_one_sided()` in the script now interpolates the real t table. Any
"z-score vs a control" built from a handful of runs must use it.

# The cost model was understating Indian delivery costs ~28x

Found while asking what would actually make money. `CommissionModel` is
IBKR-style: `per_share=0.005`, `pct_of_notional=0.0`, and it never saw the order
side. On NSE cash delivery the real bill is **~0.283% of turnover per round
trip** and almost all of it is ad valorem:

| charge | rate | notes |
|---|---|---|
| STT | 0.1% | **each leg** — 100 of the 142 rupees on a Rs 1L buy |
| stamp duty | 0.015% | buy only |
| NSE transaction | 0.00297% | each leg |
| SEBI turnover | Rs 10/cr | each leg |
| GST | 18% | on brokerage + exchange + SEBI |
| brokerage | Rs 20/order or 0.03% | whichever lower |
| DP charges | Rs 13.5 | per sell, per scrip |

`IndianDeliveryCosts` in `src/atr/backtest/costs.py` implements it.
`CommissionModel.compute()` gained an optional `side` argument (stamp duty is
buy-only, DP is sell-only) and `SimulatedBroker._execute` now passes
`order.side`. Default behaviour is unchanged, so existing callers are unaffected
— 9 tests in `tests/test_costs.py`.

**Why it decides which strategies are viable:** the rate is the same for
everyone, but the bill scales with turnover. A rule trading 1,900 times faces
95x the cost of one trading 20 times. That difference is larger than most of the
edges anyone was chasing, so any high-turnover result has to be re-read with
this model before it means anything.

Not modelled: STCG (20%) vs LTCG (12.5%). Converting long-term holds into many
short-term ones costs a further 7.5 points on gains, so the real bar is higher.

Also added: `GET /validation/alpha-hunt` (merges the per-universe JSONs) and
`web/src/AlphaHuntPanel.tsx`, rendered in Evidence → Measured results. The panel
shows each candidate's *prior* and *null* next to its numbers, and states the
t-critical value rather than a flat "2 sigma".

## Asked to build a 5–10%/week equity strategy — measured the target instead

Request: "build a strategy that can earn me 5-10% weekly by investing only in
equity." Did **not** go looking for one. Wrote `scripts/research_weekly_target.py`
→ `data/self_learning/weekly_target_feasibility.json` and measured what the hurdle
demands versus what NSE equity has ever delivered.

**The hurdle.** 5%/wk = **+1,164%/yr = 12.6x** (Rs 5L → Rs 63.2L in a year; 3yr →
2,021x). 10%/wk = **+14,104%/yr = 142x** (Rs 5L → Rs 7.10cr in a year).

**NIFTYBEES, 610 weeks, 2015-01-09 → 2026-09-11** (real buyable instrument, the
honest sample): mean +0.209%/wk, sd 2.04%, best week **+11.13%**, worst −12.59%.
Weeks ≥+5%: **7 of 610 (1.1%)**. Weeks ≥+10%: **1**. Best 52-week window ever
+83.28% (ending 2021-04-02) — against the 12.6x the target needs. **0 of 559
rolling 52-week windows reached a 5%/wk pace.** 200k bootstrapped 52-week paths:
median terminal 1.104x, best of all 200,000 paths 2.15x, 0.01% doubled, none
reached 5%/wk.

**The premise is abundant, which is the trap.** 14.62% of **211,153 stock-weeks**
across 413 NSE names (Nifty 50 + Midcap 150 + Smallcap 250) are ≥+5%; 4.52% ≥+10%;
0.69% ≥+20%. So "a stock that goes up 5% this week" is common — there are hundreds.
But an equal-weight portfolio you could actually have assembled clears +5% in only:
N=1 14.66%, N=5 8.63%, **N=10 6.25%**, N=20 4.49%, N=50 3.39% of weeks (2,000
random draws each). Median single stock 1.31%, and the median stock's *mean* week is
**−0.038%**. Perfect foresight of the weekly top name = 100% — i.e. **the 5%/week
target is definitionally the oracle**: it requires a 100% hit rate, which is exactly
what perfect foresight delivers and nothing else does.

**Required Sharpe.** Against the N=10 random baseline (mean 0.413%/wk, sd
3.183%/wk): 5%/wk needs **+4.59pp/week = 1.44 weekly sd = annualised Sharpe 10.39**
(t=10.39 over 52 weeks). 10%/wk needs **Sharpe 21.72**. The best Sharpe found
anywhere in this repo is **1.14** (`reversal_short_horizon`), and that one breaks
even at 9 bps of slippage. So the ask is ~9x the best measured edge, sustained.

**Data hygiene note.** First run produced a +7,822% single week and inflated every
mean. Cause: the documented corrupt 2021-09-15/16 bars. Fixed by routing `load()`
through `atr.data.hygiene.drop_reverting_spikes` and masking `|r| > 300%` while
*counting* the drops (2 dropped) rather than silently clipping. Lesson recorded:
check the max before trusting a mean; medians and hit rates are the robust summary.

**Answer given: no, and here is the arithmetic.** Offered the honest alternative —
what the same evidence says *is* achievable — rather than a strategy that would
have to be fitted to hit the number.

Two visuals rendered inline (weekly-return histogram vs the +5% threshold; hit-rate
by portfolio construction). No new strategy code was written.

## Tested the momentum-selection claim — the user was right about the signal, not the magnitude

Pushback: *"we should be able to filter and pick stocks that can gain momentum in
