### 1. BridgePy — FOUND TWO REAL BUGS (both now fixed, commit d5bb69a)

`bridgePy/connector.py` (52KB) is the authoritative connection protocol. It does
**not** decode payloads — it hands raw bytes to callbacks, so our hand-written
186-byte decoder was never "reinventing" anything the SDK does.

What it revealed that we had wrong:
- **MQTT auth was missing entirely.** Official: MQTT 3.1.1 + `clean_session`,
  `username_pw_set(username=<JWT preferred_username>, password="OPENID~~"+token+"~")`,
  `keepalive=20`. Ours: anonymous MQTTv5, keepalive=60. The module docstring
  already claimed auth used the JWT; the code never sent it.
- **`_handle_connect` did `int(rc)`** but paho 2.x passes a `ReasonCode`. It
  compares equal to 0, so connect *looked* fine, then raised inside the callback
  and killed the paho network thread → `is_connected` True while receiving
  nothing. Classic silent failure.

Both verified fixed against the live bridge during market hours.

Note: connector.py also contains an RSA/AES key-exchange path (struct >I lengths
for pubkey/iv/encrypted_aes_key). **Not required** — plain TLS + OPENID password
works. Probably a legacy or alternative auth mode.

### The sync exposed a real bug (worth remembering)
`_pick()` used `row[key] not in (None, "")`. **`nan not in (None, "")` is True**,
so pandas missing values passed through: absent strikes became float NaN and
absent underlyings became the literal string `"NAN"`. And `InstrumentMaster.find()`
rebuilds a row via `DataFrame.to_dict()`, where pandas' `str` dtype stores missing
as NaN — pydantic then rejected the float for the `OptionType` enum, so **every
currency future failed to resolve** with `input_value=nan`.

Fix: added `_missing()` (None / "" / NaN / NaT), applied in `_pick`,
`_parse_expiry` and `find()`. Lesson: `not in (None, "")` is not a null check.

## Live path fixed — it could not place a single order (commit fdbce26)

With the bridge working, the live path became testable. It was broken in four
ways, all now fixed and covered by 11 new tests (52 pass total).

**The critical one**: `prepare()` was called once, before any live bar.
`prepare()` is a one-shot vectorised pass over a *static* frame, so every bar
appended afterwards carried NaN indicators and the strategy skipped them all.
Measured directly:
- old behaviour (prepare once at startup): **0 orders**, last-bar `sma_fast` = NaN
- fixed (refresh as bars arrive): **1 order**, last-bar `sma_fast` = 106.73

A silent no-op, not a crash — which is the worst kind for a trading system.

Also fixed:
- `LiveConfig.warmup_bars` was declared and never used. Warmup history now
  fetched via `IiflHistoricalFeed`, capped by that setting; a failing endpoint
  degrades to a cold start rather than aborting.
- `ctx.index` was set inside a per-symbol loop, so ragged frames meant one
  index could not address them all and `ctx.row()` returned the wrong bar.
  Snapshots are now appended one row per instrument (NaN where absent),
  matching `BacktestEngine._build_frames`.
- Frames grew unbounded → `max_history_bars` caps them.
- `feed` and `client` are injectable, so the loop is testable without the bridge.

**`IiflHistoricalFeed.fetch()` was also broken**: `AttributeError: 'str' object
has no attribute 'get'`. It iterated the response body instead of
`result[0]["candles"]`, so historical candles never worked through that feed.
Candles also arrive as **positional arrays** `[ts,o,h,l,c,v]`, not dicts (which
is why `scanner.py` reads them by column). Both handled. Verified live:
RELIANCE 1259.5, INFY 1041.3, zero OHLC violations.

### Verification discipline worth repeating
When adding a regression test, prove it can fail. My first attempt at
simulating the old behaviour removed `prepare()` entirely (giving a loud
KeyError) instead of calling it once (the real silent-NaN bug). Re-running the
faithful simulation is what produced the 0-vs-1 order evidence above.

## SOLVED: the IP block was IPv6, not a missing whitelist (commit ac932fa)

User showed the portal's "Edit Details" modal: **Primary Static IP already
contained 122.177.247.238** — the correct value. So the registration was never
the problem.

Re-measuring the outbound IP was the breakthrough: four echo services returned
**two different addresses** — `122.177.247.238` (IPv4) and
`2401:4900:88f6:be42:9461:3233:3462:8bcc` (IPv6). The machine is dual-stack.

`api.iiflcapital.com` publishes both A (`23.65.124.96/99`) and AAAA
(`2600:140f:9::1741:7c60/63`, Akamai) records, so httpx was connecting over
**IPv6** — an address that was never whitelisted. The registered IPv4 was
correct and simply never used.

Decisive experiment against `/holdings`:
- default family (IPv6) -> `EC500 IP address not authorized for trading`
- `httpx.HTTPTransport(local_address="0.0.0.0")` (forced IPv4) -> **real data**

Fix: `IiflClient` now pins egress to IPv4 via `local_address="0.0.0.0"`.
Configurable: `force_ipv4` param / `IIFL_FORCE_IPV4` setting.

### Lesson
When a broker says "IP not authorized" and the registered IP looks right,
**check which address family the request actually leaves on**. A dual-stack
host silently picks IPv6. Four echo services, not one — `api.ipify.org` is
IPv4-only and reported the IPv4, which would have hidden this.

## Buy/sell signal system + Telegram (commit 48eaaac)

Built `src/atr/signals/` at the user's request: tell me when to buy, check my
holdings for sells, message me on Telegram.

**Architecture decision that matters**: the entry rules are exposed as
`SignalEntryStrategy`, which calls the *same* `eval_entry`/`eval_exit` functions
the live scanner uses. Separate implementations would make a validation pass
meaningless.

- Sell side (`atr signals sell`): risk rules over actual holdings — stop_loss,
  trailing_stop, confirmed trend_break, take_profit, rsi_overbought. Risk
  management, not prediction, so no edge required.
- Buy side (`atr signals buy`): entry rules over a watchlist, marked
  `unvalidated` until `atr signals validate` passes.

### The honest result: the entry rules FAIL out of sample
5 folds, 247 trades, **-5.05%** vs buy-and-hold **+57.39%**, Sharpe -0.06 vs
0.85, deflated Sharpe 0.926 below the 0.95 bar. The scanner reads
`data/signals/validation.json` and labels every buy signal unvalidated. Do not
present these as actionable.

### Two real bugs fixed while building
1. **`rsi()` was wrong on a monotonic rise.** `loss.replace(0, np.nan)` made a
   zero average loss NaN, then `fillna(50)` reported it as perfectly neutral.
   The strongest possible uptrend read RSI 50 — which silently qualified it as
   an RSI *pullback*. Now returns 100. This affected the scanner, the alerts,
   and every RSI-based rule. Locked down in tests/test_indicators.py.
2. **`alerts.fetch_quotes` mapped quotes positionally**, so two rules on one
   symbol misattributed the response. Now keyed by (exchange, instrumentId).

### Tuning lesson
`trend_break` fired on 10 of 17 holdings with a single close below SMA50 —
alert fatigue, not information. Added `trend_confirm_bars` (default 3
consecutive closes); now 8. Any new rule should be checked for how many
positions it flags before being trusted.

### Validation gotchas found
- The local daily cache holds only ~1 year — too short to carve into folds that
  also leave room for warmup. `atr signals validate` now fetches ~6 years
  (1,497 bars) per symbol. The API will serve 6y of dailies.
- `min_history_bars` must be comfortably smaller than the walk-forward test
  window or the strategy trades **zero times**, and "no trades" looks identical
  to "no edge". First run with `min_history_bars=210` and `test_bars=40`
  produced exactly 0 trades.

### Automation
Created recurring automation `14bee75a-5b05-4853-9846-c14e2385b5b9`
("ATR buy/sell signals to Telegram"): hourly on weekdays with a market-hours
guard in the prompt. **Constraint**: multi-hour RRULE is not expressible
(comma-separated BYHOUR is rejected), hence hourly + guard.

**Important**: the IIFL session dies at midnight IST and needs an interactive
auth code, so the automation can only succeed on days the user logs in. The
prompt handles this by sending a "session needs renewing" Telegram rather than

## Making validation trustworthy (commit 15b0428)

User: "we should train this in a good way so that we can rely on the results."
Took that as: fix the *methodology*, not hunt for a better-looking number.

### 1. The harness was handicapping what it measured
`walk_forward` ran each fold with **no history before the test window**, so
indicators were NaN for the first N bars. Worse, a strategy needing more
history than the window traded **zero times** — and "no trades" is
indistinguishable from "no edge".

Fix: `BacktestConfig.warmup_bars` — the engine runs a prefix that is neither
scored nor traded (`if self._killed or i < warmup_bars: continue`), and
`walk_forward` slices the fold to the test window. Proven by test: cold = 0
trades, warm = trades normally. OOS went -5.05% -> -0.89% purely from removing
the handicap.

### 2. Rules recomputed indicators every bar (15x speedup)
A pandas rolling op costs ~0.35ms **almost regardless of data length** —
`eval_entry` took 3.05ms on a 120-row window vs 3.20ms on a 1,500-row frame.
So per-bar recomputation dominated everything.
`precompute_indicators()` lets the strategy compute once in `prepare()`; the
rules read the columns if present and compute identically if not (verified
identical signals both ways). **3.47ms -> 0.23ms per symbol-bar.** This is what
makes sweeps finish in minutes.

### 3. Real sweeps — and the correction working as designed
`atr signals validate --search` sweeps a coarse grid. 16 combos x 5 folds =
80 trials, finished in 2m49s.

| | single config | 16-combo sweep |
|---|---|---|
| OOS return | -0.89% | **+5.91%** |
| OOS Sharpe | 0.04 | **0.18** |
| deflated Sharpe | 0.776 | **0.270** |
| hurdle (trials) | 0.1208 (5) | 0.2115 (80) |

**Searching harder made the headline better and the evidence weaker.** That is
the multiple-testing correction doing its job, and it is the clearest
demonstration of the principle the user asked for. Still FAIL.

### The real finding: the benchmark is the bar
Buy-and-hold on these 19 large caps over 2020-2026 returned **+57.39% at Sharpe
0.85**. A long/flat timing overlay starts from a structural disadvantage (it is
out of the market part of the time) and has to beat that. On this universe it
does not. Likely conclusion: **a timing overlay on liquid large caps destroys
value**; the interesting direction is a different universe (small/mid cap) or a
cross-sectional/relative-strength approach, not more tuning of these rules.

## Cross-sectional momentum — and the control that killed it (commit 176ee9f)

Next hypothesis after the entry rules failed: stop asking "is this a good buy?"
(timing) and ask "which names are strongest?" (ranking).

`CrossSectionalMomentum` — top-N by 6-month return skipping the last month,
monthly rebalance, 120 liquidity-screened names, 2020-2026, 5 folds:

| top_n | OOS return | OOS Sharpe | max DD | deflated Sharpe |
|---|---|---|---|---|
| 5 | 186.5% | 1.01 | 35.5% | 0.914 |
| 10 | 224.3% | 1.21 | 33.2% | 0.964 ✓ |
| 20 | 187.7% | 1.24 | 29.9% | 0.976 ✓ |
| 40 | 180.7% | 1.37 | 25.0% | 0.979 ✓ |

**First statistically significant result in the project** — the concentration
hypothesis was right, more names raised Sharpe and cut drawdown.

**Then the control destroyed it.** Same strategy, same universe, same cadence,
but selecting names at random instead of by momentum (top_n=20):

    momentum          : 1.24
    random (8 seeds)  : 1.25 1.52 1.23 1.39 1.06 1.78 1.69 1.37
                        mean 1.41, median 1.38, sd 0.24

Momentum sits at the **25th percentile of random** (z = -0.71). Not
significantly worse than chance, but no evidence it is better. The ranking
contributes nothing; what produced those numbers was **being long a rising
universe with concentration**.

### THE methodological lesson (most important thing learned today)
**A statistically significant Sharpe is not a useful signal.** Momentum cleared
the deflated-Sharpe bar at 0.976 and was still worthless. You need a *control*
that isolates the signal's own contribution — random selection with the same
universe, cadence and sizing. Without it we would have shipped this.

### Bug exposed and fixed
`_safe_field` returned `"_<position>"` for column names namedtuple cannot use —
but **namedtuple rejects field names starting with an underscore**, so any
frame with a `_`-prefixed column raised on every row lookup. The new
precomputed momentum columns were the first to hit it. Now uses a `c<position>`
prefix with collision handling. Tested against underscore / keyword /
tuple-method-shadowing names.

Also: `scripts/validate_cross_sectional.py` caches the fetched panel
(`data/signals/panel_nseeq_120.parquet`) so configs compare without refetching
~90s of dailies — each subsequent run is ~13s.

### Standing caveat
The universe is **survivorship-biased**: it is today's liquid names tested over
the past. Delisted names are absent, so buy-and-hold's +203% (Sharpe 1.57) is
inflated. Fixing that needs delisted data we do not have.
