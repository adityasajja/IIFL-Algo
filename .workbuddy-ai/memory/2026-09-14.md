# 2026-09-14 — Phase 2 begins: the OMS, idempotency, and a durable kill switch

Continues the Phase 1 → Phase 2 work from `2026-09-13.md`. `MEMORY.md` was rewritten

## What shipped

**`atr/execution/oms.py`** — the order state machine, pure and I/O-free. The 11
states from the brief, `VALID_TRANSITIONS` as the single definition of legality,
`assert_transition` as its only reader, `OrderDraft`, `RiskGate`/`RiskDecision`,
`LimitsRiskGate` (an adapter over the existing `RiskEngine`, not a rewrite),
`slippage_bps`, `fill_status`, `idempotency_key_for`.

Two decisions worth keeping:

- `PARTIALLY_FILLED → PARTIALLY_FILLED` is the **only self-loop**, because a second
  partial fill is an event even though it is not a state change; refusing it would
  drop a fill and desynchronise the position from the broker.
- `CANCELLED` is reachable **only** from `CANCEL_PENDING`, so an immediate broker
  cancel still writes two events and the cancel *request* is on the record.

**`atr/services/orders.py`** — `OrderService`, the transaction-owning half. Every
public method opens its own transaction; `validate()` moves `NEW → VALIDATING`,
asks the gate, then moves to `RISK_APPROVED` or `REJECTED` — all atomically. A gate
that raises rolls back and leaves the order at `NEW` (fail closed).

**`atr/services/risk.py`** + `system_state` table — the kill switch and execution
mode, durable. They were an in-process dict, so a restart re-armed trading and
dropped the platform back to paper. Now read through one service, and the OMS gate
is built from it.

**Routers** `api/routers/orders.py` and `api/routers/risk.py` — the `/api/v1/orders`
lifecycle and the `/api/v1/risk` control centre.

**Repositories** for the trading, strategy, screener and system tiers, with the
invariants enforced at the data layer (append-only events, projection written in the
same transaction, `mismatches > 0` cannot be recorded `severity="ok"`, a stopped
deployment must carry a reason).

## Bugs found — both real, neither hypothetical

### 1. pysqlite commits a released savepoint (engine-level, pre-existing)

`AppDatabase` had no explicit `BEGIN`. With pysqlite's default transaction handling,
releasing the *outermost* `SAVEPOINT` commits immediately — so a write made inside a
savepoint survived the caller's later `rollback()` while the statements after it were
undone.

Symptom in the OMS: an order sat at `NEW` while its `VALIDATING` event was committed,
breaking the projection-vs-log invariant the whole design rests on.

Fixed with the documented pairing: `dbapi_connection.isolation_level = None` on
connect plus an `engine.begin` listener emitting `BEGIN`. Regression-tested in
`tests/test_appdb_engine.py`, including that the normal path (savepoint + commit)
still persists.

**This was latent for every savepoint in the codebase, not just the new ones.**

### 2. `RiskEngine` prices an order at zero when it cannot be priced

`check_order` computes notional as `limit_price or last_price`. With neither
available the notional is `0.0`, so a MARKET order passed every notional limit
without being measured against any of them — the "unknown reported as a zero"
failure. `LimitsRiskGate` now refuses an order it cannot price when a finite
notional limit is configured. Also: `max_position_notional` defaults to
`float("inf")`, which is truthy, so a naive `if limit` read "no limit" as
"a limit is configured".

### 3. An idempotency key must not be derived for a manual order

With no `signal_id` and no `strategy_id` the hash is still stable, so two unrelated
clicks collapsed into one order — silently. The route now derives a key only for a
signal-driven order. Documented on `idempotency_key_for`.

## Design notes

- **`orders.status` is a projection, not a fact.** `OrderEventRepository.append` is
  the only writer of the column and writes it in the same transaction as the event.
  There is deliberately no `OrderRepository.update()`.
- **No `fills` table.** A fill *is* an `order_events` row.
- **`order_events.seq` + `UNIQUE(order_id, seq)`.** Timestamps are not a total order.
- **The insert *is* the idempotency guard**, inside a savepoint so a lost race leaves
  no stray `NEW` order for reconciliation to trip over.
- **Layering:** the state machine is `execution` (compute, no `appdb`); the
  transaction-owning service is `services`. `tests/test_architecture.py` enforces it
  and caught the first attempt at putting both in `execution`.
- **`extra="forbid"`** on the limits body: silently dropping a limit the operator
  believes they set is worse than a 422.

## Continued: the legacy order path, and the worst bug in the repo

The first half of the day left the legacy `POST /orders` and
`POST /trade-signals/{id}/execute` as a documented bypass. They are now on the same
path as everything else.

### Found: `OrderType.SL_MARKET` does not exist — the signal bracket crashed after placing the entry

`api/main.py:662` built the stop-loss leg with `OrderType.SL_MARKET`. The enum has
`MARKET`, `LIMIT`, `STOP`, `STOP_LIMIT`. The route places its legs in order, so the
**entry order had already been transmitted** when the `AttributeError` fired. The
operator got a 500 and no way to tell a position was open:

```
1. entry  -> placed at the exchange
2. stop   -> AttributeError            <- 500, entry still live
3. target -> never reached
```

**A live position with no stop-loss** — the one state this platform must never
produce. Two more faults in the same leg would have survived the name being right:
the trigger was passed as `limit_price` and a `broker_params["triggerPrice"]` that
`IiflBroker` never reads (it takes `order.stop_price`), and there was no idempotency
guard, so two clicks placed two brackets.

Fixed by canonicalising order types in one place — `atr.core.enums.OrderType.parse`,
which accepts `SL-M` / `SL` / `stop_market` and **refuses an unknown spelling before
anything is transmitted** — and by assembling orders only in
`atr.services.execution`. The venue is a parameter.

### `services/execution.py` — the one path to a venue

`ExecutionService.place()`: create → risk-check → submit → transmit, once. Plus
`Venue`/`VenueOutcome`, `BrokerVenue` (over the existing `Broker` ABC unchanged),
`BrokerPortfolio`, and `outcome_from_broker_order` as the single place a broker's
answer is interpreted.

Three decisions worth keeping:

- **A duplicate is never resubmitted.** If `open_order` reports the intent already
  has an order, the existing one is returned untouched. A guard the retry path can
  bypass is not a guard.
- **A venue call that raises leaves the order `SUBMITTED`.** The request went out and
  we do not know whether it landed. Writing a rejection would be a lie and a fill a
  worse one. `VenueError` carries the order id so the operator knows which order is
  now in an unknown state; reconciliation resolves unknowns.
- **A fill with no price is refused**, not recorded at zero — a zero would corrupt
  every P&L figure downstream with no trace back to the cause.

This is also the shape the paper engine needs: same lifecycle, same risk gate, same
rule layer, a different venue. Gap 4's structural blocker is gone.

### The legacy routes now require an account

An order needs an owner — `orders.user_id` is a non-null FK — and an unattributed
order is one nobody can be asked about. So `POST /orders` and
`POST /trade-signals/{id}/execute` return 401
`authentication_required_for_orders` without a principal. **This is a deliberate
behaviour change**, recorded in `API_CONTRACT.md` and gap-report §4.2: it is the one
place where "keep unversioned routes working" and "no unauthorized access on every
resource" pull opposite ways, and trading safety wins. Read-only legacy routes stay
open — the dashboard still renders without signing in.

### One source of truth for the kill switch

The in-process `_STATE` dict in `main.py` is gone; `_risk_state()` is now a view over
`RiskStateService`. It was two sources of truth for the same flag, which is exactly
what the durable store was built to remove. `POST /risk/kill-switch` now requires a
reason in **both** directions (releasing re-enables trading), and the two frontend
panels prompt for one.

## Continued again: the paper engine (gap 4 closed)

`atr/services/paper.py`. The brief's `BACKTEST → PAPER → LIVE` goal is now real
rather than aspirational, and it is real because the paper engine is **a `Venue`** —
the same `ExecutionService`, the same OMS lifecycle, the same risk gate and the same
rule layer, with `PaperVenue` in place of `BrokerVenue`. No second strategy
implementation, no parallel order model.

### Two pieces, and the split is the design

**`PaperVenue`** simulates the exchange. It models what makes a fill uncertain and
refuses to model what it cannot know:

- **A limit the market has not reached rests.** Filling a buy limit above its own
  limit is the classic paper-trading lie — it manufactures edge the market never
  offered. Same for an untriggered stop. `match()` re-evaluates a resting order
  against a later price, so a paper order behaves like one that is live rather than
  one that fills instantly and always.
- **An unpriceable order is rejected, not filled at zero.** A zero fill gives the
  position a zero cost basis and an infinite return.
- Costs default to `IndianDeliveryCosts`, **not** the IBKR-style default, which
  understates NSE delivery ~28x. A paper account costed with it reports an edge that
  does not exist.

**`PaperLedger`** is the account and holds **no state of its own**. It replays
`order_events` into the existing `atr.backtest.portfolio.Portfolio` — so a paper
position cannot drift from the orders that produced it, and `Portfolio` already
asserts `equity == cash + market value` after every fill. **No paper state table was
added**; the schema was written for this ("positions and P&L are folds over those
rows"). Reusing `Portfolio` rather than writing a paper one is the brief's
"do not create duplicate implementations" applied literally.

`order_events` gained a `commission` column so the fold is faithful. Recording it
rather than recomputing means a rate change cannot restate history — and it is what
makes the fold possible at all.

### The position-level limits now bite

`POST /api/v1/paper/deployments/{id}/orders` hands the risk gate **that
deployment's own folded portfolio**. Before this, every gate got a flat portfolio,
so `max_position_per_symbol`, `max_open_positions` and the gross-exposure check
could never fire. That was the one limit family that was unenforceable, and it is
now enforceable on the paper path.

### Two bugs found

1. **`Portfolio` leaves an unmarked position at `last_price = 0`**, so
   `unrealized_pnl` reports `(0 - avg) * qty` — a fabricated loss of the entire cost
   basis, presented as a measurement. Fixed in the ledger's snapshot: a position
   with no mark is **shown** (it is real) with `last_price`/`market_value`/
   `unrealized_pnl` as `null` and `priced: false`; `complete` is `false` and
   `unpriced_symbols` names it. Omitting the row would say "you hold nothing", which
   is a different lie.
2. **`DeploymentService.pause` let a blank reason escape as a raw `ValueError`** —
   a 500 instead of a 400 with a code. `stop` already translated it; `pause` now
   does too, through the same path.

### Decisions worth keeping

- **`reset` returns a new deployment; it does not delete.** `order_events` is
  append-only, so a paper account's history cannot be erased. The old deployment is
  stopped with the reason recorded and the response's `reset_from` names it, so the
  previous run's P&L stays readable for comparison. Deleting fills would leave orders
  whose fills had vanished and reconciliation would report mismatches the platform
  itself created.
- **A stopped deployment is terminal.** `start` only accepts `PENDING`/`PAUSED`;
  restarting a stopped strategy is a reset. Otherwise "why is this strategy still
  trading?" has no answer.
- **The price source is a named seam** (`default_price_source`), not an inline
  default — a paper fill priced from whatever is in the operator's cache is not a
  testable fill.

## The continuous paper runner — `atr/services/runner.py` (new, ~930 lines)

The gap it closes: the paper engine was **request-driven**. Prices came from the
daily parquet close, a resting limit was re-evaluated only if a client asked, and a
deployment marked RUNNING did nothing at all. `BACKTEST → PAPER → LIVE` had no
middle that actually ran.

The loop, using only existing components:

    live tick → eval_entry/eval_exit → ExecutionService → RiskEngine → OMS
              → PaperVenue → simulated fill → PaperLedger (fold of order_events)
              → positions · cash · P&L

Key decisions:

- **Sync per pass, not per tick.** A tick-driven loop at ~10 ticks/s × 50 symbols
  is 500 pandas evaluations a second for a signal that is only actionable once a
  bar. One pass per second instead; `interval_seconds` is per-deployment and the
  loop takes the minimum.
- **The pass runs in a worker thread** (`asyncio.to_thread`), so a 200 ms rule
  evaluation does not stall HTTP or the tick stream.
- **Resting orders are polled even outside market hours**; new entries/exits only
  inside. An already-accepted order should fill on any price that arrives.
- **Daily idempotency.** `acted: set[(symbol, rule, bar)]` plus an idempotency key
  derived from the bar. A rule true at 10:00 is still true at 10:01 — without this
  the loop places the same order sixty times a minute.
- **The bar key is passed as `signal_id`** to `idempotency_key_for`, not bolted on
  as an extra field. That function is the single definition of intent identity;
  appending a component would derive a key the rest of the platform cannot
  reproduce.
- **`in_market_hours()` does not handle public holidays** and says so. There is no
  market calendar in the codebase; on a holiday the feed delivers no ticks, so the
  observable behaviour is the same. Documented rather than guessed.

### The bug worth remembering

The first draft gave every deployment the **shared flat portfolio** for the risk
gate. The engine compares a SELL against `portfolio.position(symbol).quantity`, so
against a flat book every exit reads as opening a short and — whenever
`allow_short` is false — is **rejected**. Stop-losses would silently never execute,
and the dashboard would show them as armed.

Fix: `PaperRunner.order_service(loop)` folds that deployment's own `order_events`
and builds a per-deployment `OrderService`. `DeploymentLoop.bind()` resolves the
(execution, orders) pair once per pass — both are read many times inside a pass,
and folding twice would price the gate against a different book than the venue
matched against. Rebuilt every pass, because the portfolio *is* a fold; caching it
reintroduces the drift the fold exists to prevent. This mirrors what
`api/routers/paper.py` already does on the manual-order path.

### Verified, not assumed

Every sibling API was checked before use, and four assumptions in the first draft
were wrong: `_json_load_or_none` does not exist in `paper.py` (inlined a JSON
parser); `eval_exit` takes `(symbol, frame, avg_price, rules, *, quantity=)` and
**no `position=` object**; `idempotency_key_for` has **no `extra=`** parameter;
`Portfolio.position()` returns a **flat `Position`, never `None`** — so a `is None`
check silently reads as "no position" and a `0.0` is the honest test. Also:
`PaperLedger._deployment_cash` reads `capital` from the **database**, so the
runner's `initial_cash` argument is ignored and mutating `loop.row` post-hoc does
nothing.

Also hardened: `RunnerConfig.from_deployment(None)` used to raise
`AttributeError`. A row whose config cannot be read now yields an empty universe,
which `_make_loop` logs and skips — never traded on a guessed default.

It is not. `_atr_imports()` walks the **AST** with `ast.walk`, so a function-level
`from atr.api... import ...` is caught exactly like a module-level one. "Lazy import
to avoid a cycle" and "does not violate the layering" are **different claims**, and
the checker only cares about the second.

Fix, in the direction the layering allows (`api → services`, never back):

1. `services/paper.py::live_tick_source(broadcaster=None, *, resolve=None)` — takes
   the broadcaster **or** a zero-arg resolver. It never names `atr.api`.
2. `services/paper.py::install_live_source(source)` / `_LIVE_SOURCE` — a one-slot
   registry the API layer writes into.
3. `default_live_source()` reads the registry; when nothing is installed it returns
   a source that prices nothing, and `default_price_source()` falls through to the
   daily cache — the pre-existing behaviour, not a crash and not a fabricated price.
4. **New `src/atr/api/price_sources.py`** — owns the wiring. It is the *only* place
   that imports both packages, and it hands the service a plain callable. Called
   from `_on_startup` before `_start_paper_runner()`, so the first fill is priced
   from the feed rather than yesterday's close.

General rule worth keeping: when a service needs something that lives in a higher
layer, inject it or register it — never import it, however deep inside a function.

Also fixed a flaky test of mine: `test_the_background_loop_starts_and_stops` slept a
fixed 0.1s and then asserted `passes >= 1`, which fails on a loaded machine. It now
polls for the condition (up to 2s) instead of assuming a sleep is long enough.
