### The panel that mattered

**Research** is the point of the whole exercise. `/backtest` scores one
configuration on one dataset and is in-sample by construction — it is a
tempting number and a meaningless one. Research picks parameters on a training
window, scores once on the window after it, and reports the deflated Sharpe
against the hurdle implied by how many combinations were tried. The UI shows
OOS return and Sharpe against buy-and-hold, the verdict checks, the per-fold
table, and the equity curve against the benchmark. The Backtest tab now says
out loud that it is in-sample.

### Three real bugs, found by building the UI

1. **`_history_feed` read the entire cache.** `load_cached(exchange)` globs and
   deserialises every parquet file — 2,654 of them — and only then filtered to
   the 19 names asked for. A validation run took **56s**, of which ~50s was
   reading files nobody wanted. `load_cached` now takes an optional `symbols`
   filter: **1.8s**, and identical results (−9.81% OOS, same folds). Verified
   by comparing the numbers, not just by the run succeeding.
2. **`/health` blocked for ~4s.** The Postgres probe was inline. `localhost`
   resolves to both `::1` and `127.0.0.1`, so with no database running it burns
   the 2s connect timeout twice. The dashboard polls health every 15s, so the
   whole UI felt broken. The probe now runs on a daemon thread and callers get
   the last known answer: **4.05s → 0.006s**. The code comment already claimed
   "fail fast so /health never blocks" — it did not.
3. **`load_daily`'s cache fallback dropped the `ts` column.** It returned
   `frame[OHLCV]` and `OHLCV` has no `ts`, so any caller that went on to
   `pivot_to_snapshots` raised and lost the *whole* feed rather than falling
   back to the cache. Only reachable when the fresh fetch fails, which is
   exactly when the fallback is supposed to save you.

### Walk-forward on the daily cache is structurally limited

Worth remembering, because it is easy to misread as a result:

- `pivot_to_snapshots` groups by timestamp, so `total` is the number of
  **timeline bars**, not bars × symbols. The cache holds **249** trading days
  regardless of how many names you pass.
- Auto-sized windows on that give train=63 / test=62 → 3 folds.
- `signals_entry` needs ~110 bars before its rules fire, so it cannot warm up
  inside a 62-bar test window. It traded 24 times and returned −9.81% vs
  buy-and-hold −8.69%, Sharpe −2.58 vs −0.74.
- **That is not evidence of no edge.** `/research` now returns a `warnings`
  array saying so in those words, and the UI renders it above the numbers.
- The honest answer is `source=fetch`, which pulls ~2200 days per symbol via
  the API (needs a session, a few minutes). The CLI's `atr signals validate`
  already does this and deliberately does not use the cache for that reason.

## Pushed to github.com/adityasajja/IIFL-Algo (31403ea)

### The repository was destroyed mid-task, and recovered

At 08:36, while I was setting up the remote, **the entire `.git` directory
disappeared** — 527 entries, gone between two commands. The working tree was
untouched. Cause never identified; the directory had been sitting there with
stale `HEAD.lock`/`index.lock` files piling up, and something swept it.

It went to the **D: Recycle Bin**, which is what made recovery possible:

1. Parsed the `$I` metadata files for original paths. Note the format differs
   by bin version — v1 has the path at offset 24, v2 at 28. Guessing wrong
   shifts every path by 4 bytes and makes the whole bin look like it belongs
   somewhere else.
2. Copied the `$R` payloads back. Restoring *directories* is not enough: the
   first pass created empty dirs and lost 37 objects that Windows had recycled
   as folder contents. Walk each recycled directory recursively.
3. `fsck` then showed 23 missing objects — 19 blobs, 3 trees, 1 commit.

Recovered the rest by reconstruction rather than luck:

- **19 blobs**: the working tree still had the content, so `git hash-object -w`
  on the file regenerates the exact object. 19/19 recovered.
- **3 trees**: rebuilt from disk with `git mktree`. Two matched immediately.
  The third (`src/`) did not — see the .gitignore bug below.
- **1 commit** (`b127cd4`): tree derived from its child by reverting the two
  paths the child changed; parent/author/message known. Only the timestamp was
  unknown, and a commit SHA is a pure function of all of it — so I brute-forced
  a one-hour window and found it at 1789181664. **The original SHA is restored
  exactly**, so no history was rewritten.

Final: `git fsck` silent, all 14 commits' trees readable, zero missing objects.

### The bug that recovery exposed

`.gitignore` line 6 was `data/`. Unanchored, so it matched `src/atr/data/` at
every depth — meaning **the entire data layer was in zero commits**: `base.py`,
`csv_feed.py`, `history.py`, `store.py`, `synthetic.py`, `aggregator.py`,
`__init__.py`. Nothing importing `atr.data.*` could run from a fresh clone. It
was invisible locally because the files were always on disk.

Anchored to `/data/`. Found only because the tree reconstruction for `src/`
would not hash, and the 4-byte difference turned out to be a whole directory.

### Environment traps worth remembering

- **`text=True` corrupts git plumbing input.** Python translates `\n` to
  `\r\n` on Windows, so `git mktree` saw every filename with a trailing `\r`
  and produced wrong trees for an hour. Always pass bytes to `mktree` and
  `hash-object --stdin`.
- **Writes to `.git/refs/remotes/` are silently dropped** by the sandbox, and
  writes under `refs/heads/<newdir>/` are flaky. `git update-ref` reports
  success and writes nothing. Cosmetic here — `ls-remote` proves the push
  landed — but do not trust a "successful" ref write without reading it back.
- **Use Python, not curl, to probe a local server.** curl in this sandbox
  returns exit 23 with an empty body against a perfectly healthy endpoint.

## The login button that died (e55355c)

Reported from a screenshot: "why the login is disabled?"

It was not disabled by design. Three lines made `status` null at the worst
moment, and the button is `disabled={!status?.login_url}`:

    refreshAuth()       catch { setAuth(null) }        // any blip wipes it
    the modal effect    if (!auth) return              // so it never closes
    LoginBanner         disabled={!status?.login_url}  // and the button dies

Reproduced by loading the app and then blocking every `/login/status` request
(`Network.setBlockedURLs` over CDP). After the 15s poll failed the button went
to `disabled=true, opacity=0.5, pointer-events:none` and stayed there.

**That is precisely when you need it** — the backend restarting, a network
blip, a laptop waking. A dead button, unexplained, at the one moment logging in
matters. Very likely triggered by me restarting uvicorn several times while the
browser had the page open.

Fixed both ends: a failed poll now keeps the last known session state, and the
button is never a dead end — with no `login_url` it fetches one on click,
opening the tab *synchronously first* so the later navigation is still inside
the user gesture and does not get popup-blocked. On failure it says why.

Verified against the same reproduction (button stays enabled), and separately
with no status at all (click still opens and navigates to the real login URL).

### Lesson
A disabled control is a dead end unless the UI also says why and offers a way
out. "Disabled because a fetch failed" is indistinguishable from "disabled
because you may not do this", and the user has no path forward from either.

## The browser login never worked (5eb91a0)

Reported as "it's not automatically redirecting". It was not a redirect
problem at all. IIFL sends back:

    /login/callback?authcode=...&clientid=...

lowercase and unseparated. The handler declared `client_id` and `auth_code` as
**required**, so every real redirect returned `422 {"detail":[{"type":
"missing","loc":["query","client_id"]...}]}` as raw JSON and no session was
ever created. The browser login could not complete by any route.

Where the wrong names came from: `README.md` documented
`?authCode=...&clientId=...` (camelCase). The endpoint was written to match
that guess rather than the thing the broker actually sends. **A doc is not a
specification** — this is the second time in the project that trusting a
written claim instead of the observed behaviour cost real time (the first was
the IPv6 egress issue).

The handler now accepts lowercase, camelCase and snake_case. A missing
parameter returns a readable HTML page naming what was expected instead of a
bare 422.

**Verified** on a live server: the lowercase form reaches `create_session` and
comes back with IIFL's own `Invalid auth code` for a bogus code — proof it
parsed. The other spellings return the friendly page.

Worth remembering: the failed redirect meant the auth code was **never
consumed** (422 fires before `create_session`), so a code that "didn't work"
may still be live. That turned a broken flow into a recoverable one — the
manual entry form could still use it.

## "Still this?" — the IP whitelist (fe6c0c9, 7664f45)

### What is actually wrong

**Not the IPv4 fix.** That works, and the proof is a clean A/B: with the pin
every service reports `122.177.241.191`; without it `api64.ipify.org` reports
`2401:4900:88f6:...` — IPv6. So egress is correctly on IPv4.

**The registered address is stale.** `122.177.241.191` is rejected, and the
reverse DNS is `abts-north-dynamic-191.241.177.122.airtelbroadband.in` — a
*dynamic* Airtel line. It changes when the ISP re-leases, and the whitelist is
a SEBI mandate (not an IIFL policy), so it has to be re-registered each time.

Fix is the user's to make: developers.iiflcapital.com → My Apps → ⋮ → View All
Details → Primary Static IP.

### The bug that made this take three passes

**IIFL nests failures inside an envelope that always reports success:**

    {"status": "Ok", "message": "Success",
     "result": [{"status": "EC500",
                 "message": "Error : IP address not authorized for trading."}]}

I checked the top-level `status`, saw "Ok", and told the user **twelve
consecutive gated calls had succeeded when every one of them had failed.** The
measurement was wrong, not the code. Any check of this API must walk into
`result` as well — `_broker_error` now does, and treats EC926-style "nothing
here" messages as empty rather than errors.

**Lesson worth more than the fix: verify the field you are reading is the one
that carries the signal.** A success envelope is not a success. Before
concluding "it works now", make sure the thing being asserted is what was
actually observed — here, one print of the raw payload would have shown the
nested error immediately.

### Display fix

The dashboard had been rendering that failure as portfolio *data* — a table
with columns literally named `status` and `message`, so a rejected request
looked like a row of the book. Broker errors now surface as an error box.

### Made self-explaining

The rejection now carries the answer, cached and fetched only after an IP
failure has already occurred:

    ... This machine currently egresses as 122.177.241.191 — register that
    address at developers.iiflcapital.com (My Apps → View All Details →
    Primary Static IP).

## IP whitelist — the "fix forever" question

User came back at 09:39 with two screenshots:

1. Dashboard error: `limits failed: Error : IP address not authorized for
   trading. This machine currently egresses as 122.177.241.191 — register
   that address ...`
2. IIFL Edit Details dialog: `Primary Static IP = 122.177.241.191`.

The IPs match in the screenshots, yet the connection still fails. Likely
root cause: the line re-leased since the IIFL form was last saved. The
dashboard reports the *current* egress IP and the form shows the *previous*
one. The reverse DNS `abts-north-dynamic-191.241.177.122.airtelbroadband.in`
confirms the line is consumer-grade DHCP.

User wants the IP stable "forever", since Airtel re-leases every WiFi
reconnect.

### Three real options (ranked by robustness, not cost)

**1. Static IP from Airtel (cheapest if they cooperate).** Business broadband
add-on, ₹200-500/mo per public tariff; one phone call to Airtel support to
request "fixed IP". Consumer lines on `abts-north-dynamic-*` are usually
denied — Airtel wants you to upgrade to a business plan. Fastest path if they
say yes; zero code changes.

**2. Cloud VPS as the broker endpoint (most robust).** $5/mo on Hetzner CX22,
DigitalOcean basic, or Vultr Mumbai (Mumbai region = ~5ms to IIFL). Static
IPv4 is the default; never re-leases. Architecturally:

    Windows ATR  --Tailscale-->  VPS proxy  --HTTPS-->  IIFL
                                       ↑
                            registered as Primary Static IP
                                       ↑
                            runs daily `atr login` and stores JWT

The VPS holds the registered IP and the daily JWT. Home ATR talks to the
VPS over a Tailscale/ZeroTier mesh, all IIFL calls egress from the VPS.
SEBI accepts VPS static IPs (multiple Indian algo providers and the
BrokerChooser / OpenAlgo docs confirm this). This is the only fix that
doesn't depend on Airtel cooperation.

**3. VPN with a dedicated IP.** NordVPN / PureVPN-style offering, ~$3-5/mo
extra. Works in principle, but IIFL/SEBI may eventually flag known datacenter
VPN ranges, and the home internet still has to stay up for the VPN tunnel.
Worst of both worlds, listed only for completeness.

### Recommendation

Try option 1 first — one phone call to Airtel, if they say yes the problem
is solved in an afternoon with no code changes. If they refuse (likely on a
consumer line), take option 2: a Mumbai-region VPS with a small Python
gateway that mirrors `IiflClient`'s API surface, behind a Tailscale mesh.
This is ~4-6 hours of work end-to-end and gives a permanent, ISP-independent
solution.

Avoid option 3 unless the user already pays for a dedicated-IP VPN.

User was offered the choice. No code changes made today.

### React 19 upgrade (instead of patching the component)

The beui component assumes React 19 types (`inert` is a real
HTMLAttributes key; `RefObject<T>.current` is mutable). With React 18 +
`@types/react@18` the build fails on both. Upgrading was cleaner:

```bash
bun add react@^19 react-dom@^19
bun add -d @types/react@^19 @types/react-dom@^19
```

`motion@13.2.0` and `lucide-react@1.45.0` both declare peer
`react: ^18 || ^19`. `main.tsx` already used `ReactDOM.createRoot`. After
the upgrade, my React-18 workaround patches on the installed component were
reverted so it stays pristine upstream source.

### Wiring (`web/src/App.tsx`)

`AnimatedSidebarProvider` wraps the whole app. `AnimatedSidebar` composes
`Header` (ATR logo + name), `Content` (the 5 nav groups via `MenuButton`),
`Footer` (broker session ON/OFF indicator), `Rail` (drag handle for
resize). `AnimatedSidebarInset` wraps the existing `<main>`. Default state
is expanded (`defaultOpen: true`); `Ctrl+B` toggles to the focused icon
rail.

### Verified

behave like the beui demo: default = expanded with group labels and session
footer; `Ctrl+B` toggles to the icon rail.
